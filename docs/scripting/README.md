# Field scripts

Field scripts are the bytecode that drives everything the player interacts with
on a map: NPCs talking, cutscenes, doors, signposts, trainers, items on the
ground. They live in `res/field/scripts/*.s` and are written as GNU-assembler
source, but you almost never write raw instructions - every line is a macro from
`asm/macros/scrcmd.inc` that assembles to one bytecode command.

- [Command reference](command_reference.md) - all 966 script commands, grouped
  by subject, with usage counts and the C handler for each.
- [Movement reference](movement_reference.md) - the movement actions that go
  inside an `ApplyMovement` block.
- [Common patterns](patterns.md) - copy-paste recipes for the things you will
  actually write: dialogue, branching, cutscenes, giving items, warps.
- [Tooling](tooling.md) - the in-house tools: inspect a map's wiring, lint
  scripts for invisible breakage, check tile walkability.

Both reference pages are generated by
`tools/scripts/gen_script_command_reference.py`; rerun it after editing
`asm/macros/scrcmd.inc` or `asm/macros/movement.inc`. Every example on this page
and in [patterns.md](patterns.md) is assembled and linked with the real
toolchain by `tools/scripts/check_script_doc_snippets.py`, so if a command
signature changes underneath the docs, that check fails.

## Anatomy of a script file

Each map with custom behaviour owns one script file. Here is the shape of
`res/field/scripts/scripts_twinleaf_town.s`, trimmed:

```asm
#include "macros/scrcmd.inc"                        @ the command macros
#include "res/text/bank/twinleaf_town.h"            @ generated message IDs
#include "res/field/events/events_twinleaf_town.h"  @ generated LOCALID_* IDs


    ScriptEntry TwinleafTown_OnTransition            @ entry 1
    ScriptEntry TwinleafTown_CoordEvent_RivalThud    @ entry 2
    ScriptEntry TwinleafTown_Guitarist               @ entry 3
    ScriptEntryEnd

TwinleafTown_OnTransition:
    CallIfEq VAR_PLAYER_HOUSE_STATE, 4, TwinleafTown_SetPlayerHouseState5
    End

TwinleafTown_Guitarist:
    NPCMessage TwinleafTown_Text_EveryoneGoesOnAdventures
    End

    .balign 4, 0
TwinleafTown_Movement_GuitaristNoticePlayer:
    WalkOnSpotFastNorth
    EmoteExclamationMark
    EndMovement
```

Three parts, always in this order:

1. **Includes.** `macros/scrcmd.inc` resolves out of `asm/`. The text bank and
   events headers are generated into the build directory, so they are written
   as paths from the build root. A script that shows no messages omits the text
   include; a script that never names an object omits the events include.
2. **The entry table.** A run of `ScriptEntry` lines closed by
   `ScriptEntryEnd`. This is the map's public interface - `events_*.json` and
   the engine address scripts by their **1-based** position in this table, not
   by label. Entry order is therefore load-bearing: inserting a line in the
   middle renumbers everything after it. Append instead.
3. **The script bodies**, each a label followed by commands. Movement blocks
   live here too, each preceded by `.balign 4, 0`.

### Labels are internal, indices are external

`GoTo`, `Call`, `CallIfEq` and friends take a label and are resolved by the
assembler, so labels can be named and reordered freely. Anything outside the
file - an object event, a coord event, a bg event - refers to a script by its
index in the entry table. The convention throughout the repo is
`<MapName>_<WhatItIs>`, e.g. `TwinleafTown_Guitarist`,
`TwinleafTown_Movement_GuitaristNoticePlayer`,
`TwinleafTown_Text_EveryoneGoesOnAdventures`.

## Init scripts

Alongside `scripts_<map>.s`, most maps have `scripts_init_<map>.s`. This is a
separate, much smaller file that says *which* entries run automatically, and
when:

```asm
#include "macros/scrcmd.inc"


    InitScriptEntry_OnTransition 1   @ run entry 1 when the map loads
    InitScriptEntryEnd

    InitScriptEnd
```

The argument is an entry-table index, not a label. Available hooks:

| Macro | Fires |
| --- | --- |
| `InitScriptEntry_OnTransition scriptID` | when the player transitions onto the map |
| `InitScriptEntry_OnLoad scriptID` | when the map is loaded |
| `InitScriptEntry_OnResume scriptID` | when returning to the map (e.g. out of a battle) |
| `InitScriptEntry_OnFrameTable label` | every frame, gated by a var/value table |

The frame-table form opens a block of `InitScriptGoToIfEqual var, value,
scriptID` rows closed by `InitScriptFrameTableEnd` - the first row whose var
currently equals `value` wins:

```asm
    InitScriptEntry_OnFrameTable MyMap_InitScriptFrameTable
    InitScriptEntryEnd

MyMap_InitScriptFrameTable:
    InitScriptGoToIfEqual VAR_MY_CUTSCENE_STATE, 1, 4
    InitScriptGoToIfEqual VAR_MY_CUTSCENE_STATE, 2, 5
    InitScriptFrameTableEnd

    InitScriptEnd
```

Every init script ends with `InitScriptEnd`, which aligns the file. The macros
`.error` out if you nest them wrongly, so a misordered init script fails to
assemble rather than producing garbage.

## How a script gets reached

`events_<map>.json` is where a script index becomes a thing in the world. Each
of its four sections carries a `script` field:

| Section | Triggered by | Notes |
| --- | --- | --- |
| `object_events` | talking to an NPC or object | `id` becomes a `LOCALID_*` constant; `hidden_flag` hides it while a flag is set; `0` or `65535` means "no script" |
| `coord_events` | stepping into a rectangle | fires only while `var` equals `value`; `width`/`length` size the trigger |
| `bg_events` | facing and pressing A at a tile | `type` picks `BG_EVENT_TYPE_FACING`, `_WALL_SIGN` or `_HIDDEN_ITEM` |
| `warp_events` | stepping on a warp tile | no script; names the destination header |

A `script` value between 1 and 1999 is a **1-based** index into that map's own
entry table - `ScriptContext_LoadAndOffsetID` in `src/script_manager.c`
subtracts one and jumps. `0` and `65535` mean "no script". Larger values select
a *shared* script file instead, by falling into one of the ranges defined in
`include/script_manager.h`:

| Range | Shared file | Used for |
| --- | --- | --- |
| 2000+ | `scripts_common` | common routines (see `Common_*` macros) |
| 2500+ | `scripts_bg_events` | generic bookshelves, trash cans, mart shelves |
| 2800+ | `scripts_berry_tree_interaction` | berry trees |
| 3000+ | `scripts_battles` | single trainer battles, offset by trainer ID |
| 5000+ | `scripts_battles` | double trainer battles |
| 7000+ | `scripts_visible_items` | Poké Balls lying on the ground |
| 8000+ | `scripts_hidden_items` | hidden items, indexed into `include/data/field/hidden_items.h` |
| 9000+ | various | Pokémon Center floors, contests, day care, poffins, ... |
| 10000+ | `scripts_field_moves` | Cut trees, Rock Smash boulders, Strength boulders |

That is why a route full of trainers has almost no script entries of its own:
an ordinary trainer sets `trainer_type` to `TRAINER_TYPE_NORMAL` and puts the
`TRAINER_*` constant straight in `script`, which lands in the 3000 range and
runs the generic `Battles_Trainer` flow in `scripts_battles.s`. `data: [N]` is
that trainer's sight range. Only write a script for a trainer when they need
bespoke behaviour - a gym leader, a rival, a scripted defeat.

## Placing an object event

An NPC needs a tile that is actually walkable. Getting this wrong is invisible
until you load the map, so check it from the repo rather than guessing:

```
$ python3 tools/scripts/check_tile.py MAP_HEADER_TWINLEAF_TOWN 112 888 --map 6
(112,888): walkable  collision=0  TILE_BEHAVIOR_NONE

  . walkable   # blocked   ~ water   D door   + other behavior   X query tile

        6789012345
  z   882 ####......
  z   883 ####......
  z   884 ####.....#
  z   885 #D##......
  z   886 ..........
  z   887 ..........
  z   888 ....X.....
```

It exits 0 for a walkable tile, 1 for a blocked one and 2 on error, so it also
works in a check. The tool decodes the same `terrainAttributes` grid the engine
reads - bit 15 is collision, the low byte is the tile behavior - so doors, water
and ledges each report distinctly. Keep NPCs off door tiles *and* off the tile
in front of a door, or they block the entrance.

It reads static terrain and the map-prop list only. It does not know about
dynamic collision (Cut trees, Strength boulders) or about other object events,
so still sanity-check against the existing `object_events` coordinates.

Give a standing NPC `movement_range_x` and `movement_range_z` of `0` so it
cannot wander somewhere awkward; anything higher lets it roam that many tiles.

## Text

Message IDs come from `res/text/<bank>.json`, one bank per map:

```json
{
  "key": 18219,
  "messages": [
    { "id": "TwinleafTown_Text_BigThud", "en_US": "{SIZE 200}Thud!!{SIZE 100}\r" }
  ]
}
```

`msgenc` turns that into `res/text/bank/<bank>.h` in the build directory,
`#define`-ing each `id` to its index, which is what `Message` takes. Line
control lives in the string itself: `\n` is a new line in the same box, `\r`
waits for a button press and clears, `\f` scrolls. `{STRVAR_1 3, 0, 0}` prints
the string that `BufferPlayerName 0` (or `BufferRivalName`, `BufferItemName`,
...) loaded into slot `0`.

## Flags and variables

Both come from `generated/vars_flags.txt`, a flat ordered list where position
determines the numeric value.

- **Flags** are single bits: `SetFlag`, `ClearFlag`, `GoToIfSet`, `GoToIfUnset`.
- **Variables** are 16-bit: `SetVar`, `AddVar`, `GoToIfEq`, `GoToIfGe`, ...

`VAR_0x8000` through `VAR_0x800D` are scratch registers, valid only for the
duration of one script run. Two have names worth knowing: `VAR_RESULT`
(`VAR_0x800C`), which nearly every `Check*`/`Get*` command writes to, and
`VAR_LAST_TALKED` (`VAR_0x800D`). Anything that must survive leaving the map
needs a persistent var or flag. `FLAG_MAP_LOCAL_*` are reused per map and are
cleared on transition - good for cutscene bookkeeping, useless for progress.

To add a flag or var, insert a name into `generated/vars_flags.txt`. Appending
inside the right section is safe; reordering existing entries changes their
values and invalidates save data.

## Wiring a new script file into the build

Creating `res/field/scripts/scripts_my_map.s` is not enough - the file has to be
assembled, packed into the `scr_seq` NARC at a known index, and pointed at by a
map header. Work through this list:

1. **Write** `res/field/scripts/scripts_my_map.s` and, if the map needs
   automatic scripts, `res/field/scripts/scripts_init_my_map.s`.
2. **Register both files** in `res/field/scripts/meson.build`, in the
   `scr_seq_files` list.
3. **Register both names** in `res/field/scripts/scripts.order`, without the
   `.s` extension. This file is byte-for-byte the same order as the meson list
   and controls the NARC index, so append to both in the same position. It uses
   LF line endings. (`res/field/events/zone_event.order` is the same idea for
   events, but uses CRLF - match whatever the file already has.)
4. **Add a text bank** if the script shows messages: create
   `res/text/my_map.json` and add `TEXT_BANK_MY_MAP` to
   `generated/text_banks.txt`. The filename must be the constant minus the
   `TEXT_BANK_` prefix, lower-cased; `res/text/meson.build` picks the file up
   from the constant list, so there is nothing else to edit.
5. **Add an events file** if the map has NPCs or triggers: create
   `res/field/events/events_my_map.json`, then add it to both
   `res/field/events/meson.build` and `res/field/events/zone_event.order`.
6. **Point the map header at it.** In `include/data/map_headers.h`, set
   `.scriptsArchiveID = scripts_my_map`, `.initScriptsArchiveID =
   scripts_init_my_map`, `.msgArchiveID = TEXT_BANK_MY_MAP` and
   `.eventsArchiveID = events_my_map`. Those symbols come from the generated
   `.naix` headers, so they only exist once steps 2-5 are done. See
   [editing map headers](../maps/editing_map_headers.md).
7. **Build** with `make rom`. Assembly errors point at the `.s` file; a missing
   `.naix` symbol means a step above was skipped. Use `make rom`, not a bare
   `make`: the default target is `release`, which re-blesses the SHA-1
   manifests in `platinum.us/` once the ROM is built, so a bare `make` quietly
   records your change as the new expected output. Bless deliberately, when the
   change is finished - see [checksums and blessing](../checksums_and_blessing.md).

Reusing an existing map's script file needs none of this - just point another
header's `.scriptsArchiveID` at the same symbol.

### Adding to an existing script file

Much more common, and much shorter:

1. Append a `ScriptEntry` to the table - **append**, never insert, or every
   later index shifts.
2. Write the script body.
3. Add any new messages to the map's `res/text/*.json`.
4. Reference the new entry by its 1-based index from `events_*.json`, or from
   `scripts_init_*.s` if it should run automatically.

## How the build assembles a script

`tools/scripts/make_script_bin.sh` runs each `.s` through the C preprocessor,
then `enumproc` (which expands generated enums into `#define`s), then
`arm-none-eabi-gcc` as an assembler, then `objcopy -O binary`. The include path
is `include/`, `asm/` and the build directory, which is why
`#include "macros/scrcmd.inc"` and `#include "res/text/bank/foo.h"` both
resolve. `nitroarc` then packs the binaries into `scr_seq.narc` in
`scripts.order` order and emits `scr_seq.naix` with one `#define` per file.
